# Leave-Bot 🚂

Reminds a WhatsApp group **the day before IRCTC ticket booking opens** for every office **break** — 2 or more continuous days off (holidays + Sundays combined) — so everyone can grab train tickets the moment the 60-day booking window opens.

## How it works

- Holiday data lives in [data/holidays-2026.json](data/holidays-2026.json) (hand-verified from the office holiday list).
- IRCTC opens booking 60 days before the journey date. The bot sends three alerts per break:
  - **Outbound** 🎫 — for a break starting on date X, messaged on **X − 61**: "Tomorrow is ticket opening for *{holiday}* — N days leave".
  - **Return** 🔁 — booking for the return journey (break end date Y) opens Y − 60, messaged on **Y − 61**: "Return ticket opens tomorrow".
  - **Tatkal** ⚡ — tatkal opens at 11 AM (AC 10 AM) one day before travel. For people leaving the night before the break, messaged on **X − 2** ("tatkal for tomorrow-night's train opens TODAY at 11 AM").
- On the exact alert day the "opens tomorrow" wording is used. If the bot was down that day, a **catch-up** fires on the next check instead — "Ticket booking is already open — book ASAP" (outbound/return, any time while the window is open) or "Tatkal opens TODAY at 11 AM" (one day before the break). Sent notifications are remembered in MongoDB (or a local state file in dev) so the same alert is never repeated. The check runs daily at 9:00 AM IST **and once at every boot** as soon as WhatsApp connects, so a fresh deploy immediately announces any break whose booking window is already open. Every message ends with "_note: this is an automated message_".
- **Missing next year's list**: once the alert horizon (~76 days ahead) reaches a year with no `data/holidays-<year>.json`, the bot posts a monthly warning in the group ("Holiday list for 2027 is not updated!") until the file is added — starting around early/mid November.
- Messages are posted via [Baileys](https://github.com/WhiskeySockets/Baileys) — the bot logs in as a linked device of a real WhatsApp number (one-time QR scan) over WhatsApp's WebSocket protocol directly, no browser. (Previously whatsapp-web.js, whose headless Chromium needed 300–500MB and OOMed Render's free 512MB tier.)

Breaks detected for 2026: 3-day — **Mar 20–22, Apr 3–5, May 1–3, Aug 14–16, Oct 2–4, Nov 7–9, Dec 25–27**; 2-day — **Jan 14–15, Jan 25–26, Feb 14–15, Jun 6–7, Jul 4–5, Sep 5–6**.

## Deploy to Render

1. Push this repo to GitHub, then in Render choose **New → Blueprint** and pick the repo ([render.yaml](render.yaml) configures everything, on the **free** plan).
2. In the Render dashboard set `MONGODB_URI` to a free [MongoDB Atlas](https://www.mongodb.com/atlas) connection string — the free tier has no disk, so the WhatsApp session, sent-notification state and holiday calendars live in MongoDB. Also set `GROUP_INVITE_CODE` to the WhatsApp group invite link (e.g. `https://chat.whatsapp.com/AbCdEf123`), or `GROUP_NAME` to the exact group name if the bot's number is already a member.
3. After the deploy, open `https://<your-app>.onrender.com/qr` and scan the QR with the phone that owns the bot's WhatsApp number (**WhatsApp → Linked devices → Link a device**). One-time — once the log shows "session saved to MongoDB", the login survives restarts.
4. Verify with `https://<your-app>.onrender.com/status`, then send a test message:
   `curl -X POST "https://<your-app>.onrender.com/test?token=<TEST_TOKEN>"`
   (`TEST_TOKEN` is auto-generated by Render — find it in the service's environment tab.)
5. Set up the keep-alive pinger (below) — without it the free service sleeps and the 9 AM check never runs.

### Keep-alive on the free tier (UptimeRobot)

Render's free tier spins the service down after ~15 minutes without **external** HTTP traffic — its own `healthCheckPath` probe doesn't count. An external monitor pinging the public URL keeps it awake:

1. Sign up free at [uptimerobot.com](https://uptimerobot.com) → **Add New Monitor**.
2. Monitor type **HTTP(s)**, URL `https://<your-app>.onrender.com/health`, interval **5 minutes**.
3. Done — the periodic GET counts as external traffic and prevents spin-down, and you get downtime alerts for free. ([cron-job.org](https://cron-job.org) works the same way.)

Free-tier caveats:

- **No persistent disk** — the filesystem is wiped on every deploy/restart. The WhatsApp session and sent-notification state survive because they live in MongoDB (`MONGODB_URI`); without it, every restart would need a fresh QR scan.
- If the service was asleep or down past 9 AM on an alert day, the alert is caught up ("booking already open") on the next boot or 9 AM check — dedup keys in MongoDB stop it from repeating.
- One always-on service uses ~744 of the 750 free instance-hours/month — it fits, but only one such service per account.

## Endpoints

| Endpoint | What it does |
|---|---|
| `GET /health` | Health check (public — used by Render's healthCheckPath and the keep-alive pinger) |
| `GET /` | Same as `/health` (public) |
| `GET /login`, `/logout` | Login page — username/password from `ADMIN_USER` / `ADMIN_PASS` env |
| `GET /status` | Auth state, resolved group, pending notifications (login required) |
| `GET /qr` | Shows the WhatsApp QR code when a scan is needed (login required) |
| `POST /test?token=…` | Sends a test message to the group (login **or** `TEST_TOKEN`) |
| `POST /run?token=…` | Runs the daily check immediately (login **or** `TEST_TOKEN`) |

## Local development

```bash
npm install
npm test                                  # unit tests for break detection
FAKE_TODAY=2026-09-08 npm run dry-run     # prints what would be sent, no WhatsApp needed
cp .env.example .env                      # optional — every setting has a default (login admin/admin,
                                          # port 3000, 9 AM IST cron, file storage); .env only overrides
npm run start:local                       # real run: scan QR at http://localhost:3000/qr
npm run dev                               # same as start:local, but auto-restarts on src/ changes
```

## Updating for a new year

1. `npm run ingest -- <image-of-new-holiday-list>` — OCRs the image, cross-checks every date against the weekday printed in the image, and writes `data/holidays-<year>.json` (a `.draft.json` if the file already exists).
2. **Review** the printed table and any ⚠ warnings against the image.
3. With `MONGODB_URI` in your `.env`, the final (non-draft) calendar is **uploaded to MongoDB automatically** — the hosted bot picks it up on its next check, no redeploy needed. Also commit the JSON so the repo stays the source of truth.
